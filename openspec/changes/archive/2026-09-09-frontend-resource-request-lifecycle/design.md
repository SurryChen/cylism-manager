## Context

`useAsyncResource` 已用于首页，并能为一个 loader 保存 data、loading、error，取消旧请求以及忽略旧响应。应用、服务器与监控页仍直接调用通用 `api`：应用页观察项目/环境路由参数，服务器页观察区段，监控页观察标签与趋势范围。这些触发条件都可能在上一请求结束前再次变化。

## Goals / Non-Goals

**Goals:**

- 让上述三页的读取请求在状态变化或组件卸载时不再采纳过期结果。
- 让页面通过命名的领域 API 调用，而非散布 REST 路径和查询字符串。
- 保留每个页面现有的独立加载粒度，避免一次失败遮蔽不相关区域。

**Non-Goals:**

- 不修改 REST 接口、响应字段或后端实现。
- 不将创建、更新、删除等用户命令迁入通用资源层。
- 不引入 Pinia、Vue Query、全局缓存、自动重试或轮询框架。
- 不拆分本次涉及的大型页面组件。

## Decisions

### 领域 API 保持为扁平模块

新增 `api/applications.js`、`api/servers.js`、`api/monitoring.js`，导出语义化读取函数，并把最后一个可选参数传给通用 API 客户端。

理由：页面保留业务编排，API 模块仅拥有端点与参数序列化；无需新目录或仓储层。备选的单一 `api/index.js` 会继续让路径和参数散落在页面内；引入客户端类或全局 store 对当前规模没有收益。

### 只迁移会被重新触发的读取流

应用页迁移项目、工作台、应用列表、发布历史与概览读取；服务器页迁移服务器列表、资源统计、网络诊断和按服务器统计读取；监控页迁移状态刷新、趋势、工作负载与 targets 读取。写操作继续直接经领域 API 调用，并在成功后刷新相关资源。

理由：读取流有竞态和可取消性需求；写操作需要保留按钮禁用、表单校验和命令型错误文案。备选的“所有 API 均强制走资源对象”会将一次性命令误建模为可重放读取。

### 一个页面可使用多个独立资源

不把页面的所有数据合成一个大 loader。有关联且必须原子更新的读取（例如监控状态、节点、存储类）可用同一个 loader 内部 `Promise.all`，共享一个 signal；不相关区域维持各自的 resource。

理由：保留已有的局部 loading/error 体验，并避免一个慢接口阻塞其他区域。备选的单一页面资源无法表达监控趋势、targets 等独立状态。

### 使用现有 `useAsyncResource`，仅在发现缺口时最小扩展

页面通过 `refresh(...args)` 触发读取，loader 接收 `{ signal }`。路由/筛选 watch 使用 resource 的 refresh；资源在组件 scope 释放时自行取消。

理由：首页已验证该模式，避免出现第二套请求生命周期实现。

## Risks / Trade-offs

- [将 `ref` 改为 resource data 导致模板或计算属性遗漏] → 逐页搜索原状态引用，先补页面回归测试，再迁移并运行全量前端测试。
- [复合加载器中后一个异步步骤使用过期前置数据] → 复合 loader 接受同一 signal，并在 resource 采纳结果前保持局部变量，不提前写页面状态。
- [写操作成功后刷新错误被误报为命令失败] → 命令和刷新使用独立错误处理，成功写操作后仅更新对应读取资源。
- [监控迁移轮询与卸载时机冲突] → 保留现有 timer 清理，轮询调用 resource refresh；卸载由 composable 取消在途请求。

## Migration Plan

1. 先为领域 API 和 resource 竞态行为建立测试。
2. 依次迁移应用、服务器、监控页面，每页完成后运行关联 Vitest 测试。
3. 运行全量前端测试与生产构建，再运行 `go test ./...` 和 `go build ./...`。
4. 如有回归，可仅恢复对应页面到直接读取调用；服务端和数据迁移均不受影响。

## Open Questions

- 无。现阶段不加入缓存和自动重试；后续可基于真实请求频率单独设计。
