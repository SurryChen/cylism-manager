## Context

节点镜像源是规则管理页，不应承担实时节点仪表盘的职责。系统已有密度较低的表格/列表工作台和模态交互模式；本页应复用该模式，将按节点的诊断与有风险操作放在独立弹窗中。

## Decisions

### 1. 单行规则列表

规则主区域使用现有 `data-table` 列表模式：名称、Registry、镜像地址、验证状态、启用状态、最近一次应用状态和操作。端点使用截断与换行保护；“检测”“选择节点应用”“查看记录”“编辑”“删除”留在行尾。应用记录从 `node_statuses` 读取，但仅在“查看记录”弹窗中显示，主列表不渲染详情或远端文本。

### 2. 顶部节点配置弹窗

顶部新增“查看节点配置”按钮。打开弹窗后列出平台管理的集群节点；用户选择一个节点并触发检查，前端向既有检查端点提交受限的 `server_id`。服务端仅接受库存中 `cluster_role` 非空的节点 ID，不接受主机、路径、命令或 YAML 内容。

弹窗依次展示：节点名称、检查时间、匹配/缺失/漂移状态、期望规则、节点当前的安全配置摘要和结构化差异。保留“检查全部节点”作为次级动作，便于运维批量排查，但结果仍在弹窗内的列表中展示。

### 3. 受确认的 K3s 服务重启

弹窗中每个已选择且具备 SSH key 的节点可使用“重启 K3s 服务”。点击后必须先经过确认，明确说明工作负载可能短暂不可用。后端调用固定命令检测 `k3s.service` 与 `k3s-agent.service`，只重启发现的一个服务并确认 active 状态；不接受任意 unit、主机或命令，不写 `registries.yaml`，不重启宿主机。

操作结果仅返回安全的状态和有限说明，并记录不含 SSH 输出或配置内容的审计事件。

### 4. 安全与兼容

实际配置读取仍在服务端解析后立即丢弃原文，只返回 registry、无 userinfo 的 endpoint、认证是否存在与 TLS 标记。`POST /api/node-registry-mirrors/inspect-actual-config` 保持无 body 时检查全部节点的兼容行为，body 中仅可选 `server_id`。

## Risks

- 重启 K3s 影响节点工作负载：显式确认、固定服务单元、审计记录和操作中状态降低误触风险。
- 单节点检查可能被绕过：服务端按管理库存与 cluster role 校验，不信任前端节点字段。
- 应用日志可能过长或包含不适合主页面的信息：仅在按需记录弹窗中显示既有持久化摘要。
