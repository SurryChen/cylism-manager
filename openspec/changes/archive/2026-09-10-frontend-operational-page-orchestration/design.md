## Context

前端领域 API 已基本完成收口，页面现在通过命名 API 模块发起请求，并已有 `useAsyncResource` 与 `usePolling` 两个生命周期原语。`Servers.vue` 仍同时编排服务器 CRUD、SSH 检测、集群导入、资源监控、网络诊断、统计图表和终端入口；`Workloads.vue` 同时编排五类资源清单、Pod 筛选、工作负载详情及多种变更弹窗。两者的功能边界是合理的，但页面内部的读请求、详情请求和 mutation 状态仍有共享变量，测试也有部分旧的 `api/index.js` mock。

本次设计只处理页面编排和可验证的状态契约，保持当前路由、接口和视觉工作流不变。

## Goals / Non-Goals

**Goals:**

- 将服务器和工作负载页面的独立读取、详情读取、轮询和 mutation 状态明确分开。
- 保留最近一次成功数据，避免一次刷新失败导致已展示内容消失。
- 在快速切换目标、刷新或离开页面时，保证最新请求胜出且已取消请求不产生用户错误。
- 变更失败时保留操作上下文、表单输入和重试入口。
- 为关键竞态、生命周期和失败路径建立页面级回归测试。

**Non-Goals:**

- 不修改后端 REST endpoint、请求 payload、响应格式或 Kubernetes 行为。
- 不引入 Pinia、全局错误总线、缓存框架或新的第三方依赖。
- 不改变路由结构、页面信息架构或整体视觉设计。
- 不将 `ChatDrawer.vue`、其他运维页面或所有旧测试一次性重构。
- 不为了缩短行数而进行没有独立行为边界的组件拆分。

## Decisions

### 以页面内资源为边界，而不是引入全局 store

服务器清单、资源概览、网络诊断和单服务器统计具有不同刷新时机；工作负载清单、展开详情和回滚版本也有不同生命周期。继续使用页面内多个 `useAsyncResource`，让每个资源自行取消、保留数据并暴露错误，能够覆盖当前需求且无需跨路由共享状态。

备选方案是引入全局 store 或统一请求缓存。它们会增加缓存失效和卸载管理的复杂度，而当前需求只涉及单页面生命周期，因此不采用。

### mutation 状态按操作类型隔离

服务器的保存、删除、导入、解除绑定，以及工作负载的扩缩容、镜像更新、回滚分别拥有自己的提交状态和错误显示区域；如果 UI 仍只能同时进行一个操作，也至少通过操作类型和目标 ID 保证错误不会显示到无关弹窗。

备选方案是继续使用一个页面级 `mutationLoading`/`mutationError`。这种方式改动少，但会让一个失败覆盖另一个操作的反馈，也无法稳定保留重试上下文，因此不采用。

### 只抽取有独立生命周期的 composable

优先在页面内明确资源 loader、刷新和操作函数；只有当资源监控轮询、网络诊断或工作负载详情状态具备独立测试价值时，才抽取扁平的小型 composable。模板仍保留在页面中，避免形成多层组件树。

备选方案是按每个 modal 或表格拆出多个组件。此方案会增加 props/emit 传递和测试维护成本，且不能自动解决请求竞态，因此不作为本次默认策略。

### 测试直接 mock 领域 API

`Servers.test.js` 使用 `api/servers.js`，`Workloads.test.js` 使用 `api/kubernetes.js`，测试请求参数、AbortSignal、旧响应隔离、失败后的 UI 状态和卸载行为。`api/index.js` 仅继续在真正需要 token/transport 的测试中 mock。

备选方案是保留底层通用 API mock。它无法验证页面是否遵守已建立的领域边界，且会掩盖错误的 endpoint 归属，因此不采用。

## Risks / Trade-offs

- [重构状态时意外改变现有操作顺序或文案] → 先补行为测试，保持 API 调用、payload、确认流程和成功后刷新顺序不变。
- [请求取消在 mock 或旧浏览器环境中不可用] → `useAsyncResource` 同时使用 AbortSignal 和 request ID 校验，取消失败时仍能忽略旧结果。
- [局部错误过多导致模板反馈分散] → 每个错误只归属一个可见操作区域，并保留页面级错误作为无明确归属的兜底。
- [测试中的旧 mock 形态导致迁移成本上升] → 先迁移两个高频页面，保留 API 模块未传 options 时的兼容调用形态。
- [抽取 composable 后调试路径变长] → 只抽取有独立生命周期和测试收益的逻辑，禁止为单个展示片段创建文件。

## Migration Plan

1. 盘点两个页面的读资源、mutation、弹窗和轮询状态，先为现有行为补充失败、竞态和卸载测试。
2. 在不改变接口契约的前提下，隔离服务器资源状态和工作负载清单/详情/mutation 状态。
3. 将页面测试切换到对应领域 API mock，并补充 deferred promise、AbortSignal 和 last-successful-data 断言。
4. 运行前端测试与构建，再运行后端回归测试、构建、`openspec validate --all --strict` 和 `git diff --check`。
5. 若出现回归，可回退本 change 的页面和测试改动；无数据迁移和部署步骤。
